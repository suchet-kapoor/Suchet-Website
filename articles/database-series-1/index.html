Data Types: Integers, Decimals and Strings

Two questions before any SQL: does MySQL have a Boolean type, and what does DECIMAL(10,2) actually mean? Chapter one of a database series starts at the smallest decision you make about a column — and the one you almost never revisit.

Suchet Kapoor November 2026 · 9 min read

Do you know there is no Boolean data type? Do you know what DECIMAL(10,2) stands for?

If not, then the basics of databases are worth reading properly. In the world of AI, the layer that stays accountable to humans is the database layer — the model can guess, but a column type cannot.

This is the first chapter of a basics series that will take us from data types to indexing, pagination, sorting and joins. Everything is raw SQL, so that later we can look at what Hibernate generates and know exactly what it is doing.

Let's get started.

Two ways to get a database

Broadly, a database can come from two places:

  • Self-managed — you install MySQL or Postgres, you own the server, the config and the backup.
  • Framework-managed — Hibernate or another ORM reads your entity classes and creates the tables for you.

Both are fine. But the second one hides the first one, and the moment a query is slow, you need to know what is underneath. So we stay with the raw version.

Integer data types

An integer type is just a fixed number of bits, and the number of bits decides the range. MySQL ships five of them:

MySQL integer types
Type Size Signed range Unsigned range
TINYINT 1 byte · 8 bits -128 → 127 0 → 255
SMALLINT 2 bytes · 16 bits -32,768 → 32,767 0 → 65,535
MEDIUMINT 3 bytes · 24 bits -8,388,608 → 8,388,607 0 → 16,777,215
INT 4 bytes · 32 bits -2,147,483,648 → 2,147,483,647 0 → 4,294,967,295
BIGINT 8 bytes · 64 bits -9,223,372,036,854,775,808 → 9,223,372,036,854,775,807 0 → 18,446,744,073,709,551,615

Every time you add a byte, you double the available range. That is the whole trade: one extra byte buys you twice the numbers. A TINYINT is enough for a person's age; a BIGINT is what you reach for when the id comes from somewhere else and you have no control over how big it gets.

Signed and unsigned

By default every integer is signed, which means half of its range is spent on negative numbers. Add UNSIGNED and MySQL drops the negatives and spends the whole range on zero and above — which is why TINYINT UNSIGNED reaches 255 instead of stopping at 127.

That makes UNSIGNED the right choice for anything that can never be negative: ages, counters, quantities, ids. It is also the wrong choice if a future -1 needs to mean “unknown” — a decision that is much cheaper to make now than to migrate later.

Practical rule

Use INT or BIGINT for primary keys. They give you so much range that you will never think about it again — and if you are not sure whether INT is enough, it probably isn't.

The classic first table looks like this. Run it in any MySQL client — and if installation is where you got stuck, message me and we will fix that too:

CREATE TABLE employee (
  id  BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  age INT DEFAULT 0
);

UNSIGNED because an id is never negative. AUTO_INCREMENT because you never want to invent the next id by hand. DEFAULT 0 on the age so that an insert that forgets the column still succeeds.

There is no Boolean

Remember the question from the start? Here is the answer: MySQL has no native Boolean type. BOOLEAN exists only as a synonym — declare a column as BOOLEAN and MySQL quietly creates a TINYINT(1). TRUE is stored as 1, FALSE as 0, and any non-zero value you read back counts as true.

Pretty dope — and a good early lesson: in MySQL a type name is not always a type. Some of them are aliases, and knowing which is which saves you from a very confusing column.

Decimal data types

Integers cover whole numbers. The moment you store a price, a salary or a measurement, you need one of four decimal types — and they split cleanly into two families:

The four MySQL decimal types
Type Family Size What it is for
DECIMAL Exact Variable, ~4 bytes per 9 digits Money, balances, anything that must add up to the exact same number twice
NUMERIC Exact Same as DECIMAL An alias — in MySQL the two are the same type
FLOAT Approximate 4 bytes About 7 significant digits; measurements, where a tiny error is acceptable
DOUBLE Approximate 8 bytes About 15–17 significant digits; the same idea with more room

Exact means the database stores the digits you typed. Approximate means it stores the closest binary fraction it can, and shows you a decimal that is usually — not always — the number you meant. That single difference is the reason DECIMAL exists.

DECIMAL(10,2) is not “ten point two”

The two numbers inside the brackets are a budget, not a value:

  • 10 — precision. The total number of digits the column can hold, on both sides of the decimal point.
  • 2 — scale. How many of those digits sit after the decimal point.

So DECIMAL(10,2) allows ten digits in total, two of which are decimals — which leaves eight digits before the point. The largest value it can store is 99,999,999.99, and the smallest step it can represent is 0.01. Nothing smaller than a paisa exists in that column.

Read it as: eight digits before, two digits after. If you need four decimal places — exchange rates, unit prices — ask for DECIMAL(12,4). The precision limit in MySQL is 65 digits, the scale limit is 30.

Storage

DECIMAL packs nine digits into four bytes. So DECIMAL(10,2) — ten digits — costs five bytes, while DECIMAL(12,4) — twelve digits — costs six. It is not free, but it is cheaper than the bug you get from using FLOAT for money.

Adding the columns and inserting a value looks like this:

ALTER TABLE employee
  ADD dec_c  DECIMAL(10,4),
  ADD dec_c4 DECIMAL(12,3),
  ADD float_c FLOAT;

INSERT INTO employee (dec_c) VALUES (100.439340);  -- stored as 100.4393
INSERT INTO employee (float_c) VALUES (100.439340); -- stored as ~100.43934

The DECIMAL(10,4) column keeps exactly four decimal places, so the extra 40 is rounded away the moment it is written. The FLOAT column keeps something close to the same value, and how close depends on the binary representation — which is the part nobody wants to reason about at 2 AM.

Why 0.1 + 0.2 is not 0.3

In binary, 0.1 has no exact representation — the same way 1/3 has no exact decimal representation. FLOAT and DOUBLE store the nearest binary fraction they can and hope you never compare the result.

SELECT 0.1 + 0.2 = 0.3;      -- 1 (true):  MySQL treats these literals as DECIMAL
SELECT 0.1e0 + 0.2e0 = 0.3;  -- 0 (false): the e0 forces them to DOUBLE

That is the whole argument in two lines. The e0 is not decoration — it is the difference between “the number you typed” and “the closest binary fraction to the number you typed”. Use DECIMAL for money. Use FLOAT when you genuinely mean “approximately” — sensor readings, scores, coordinates — and never when the number has to match a bank statement.

String data types

Strings divide into three groups: fixed length, variable length, and the specialised ones for huge text, raw bytes and small lists.

MySQL string and byte types
Type Length Best for
CHAR(n) Fixed, 0–255 chars Codes that are always the same width — country, currency, hashes
VARCHAR(n) Variable + 1–2 byte prefix Names, emails, URLs — almost everything else
TINYTEXT 255 bytes A short note
TEXT 65,535 bytes Paragraphs, comments
MEDIUMTEXT 16 MB Article bodies, logs
LONGTEXT 4 GB Something you should probably put in a file store instead
BINARY(n) / VARBINARY(n) Fixed / variable bytes The same idea as CHAR/VARCHAR, but for raw bytes
TINYBLOB → LONGBLOB 255 B → 4 GB Images, files — again, usually object storage is the better answer
ENUM 1–2 bytes A fixed list of allowed strings, stored as an index
SET 1–8 bytes Any combination of up to 64 fixed strings, stored as a bitmask

CHAR vs VARCHAR: paying for space either way

CHAR is fixed length. Declare CHAR(32) and every row reserves room for thirty-two characters, whether you store one character or thirty-two. Short values are padded with spaces, and MySQL strips those trailing spaces back off when you read the column.

VARCHAR is variable length. It stores what you gave it, plus one byte (two bytes if the column can exceed 255 characters) that records how long the value is. So 'suchet' in a VARCHAR(32) costs six bytes of text and one byte of length — seven bytes, not thirty-two.

Storing the value 'suchet' — 6 characters
Column Space reserved Actually used
CHAR(32) 32 characters 32 characters — padded with spaces
VARCHAR(32) up to 32 characters + 1 6 characters + 1 byte of length = 7

So why would anyone choose the wasteful one? Because fixed width is predictable: the database knows where every row starts without decoding a length prefix, and it can update a value in place instead of shuffling the row. For a two-letter country code or a 64-character hash, that is a good trade. For a name that might be "Li" or "Venkatanarasimharajuvaripeta", it is not.

The byte count is per character set

The arithmetic above assumes one byte per character. Under utf8mb4 — which is what you should be using — a character can take up to four bytes, so CHAR(32) can reserve up to 128 bytes. This is also why a table full of long VARCHAR columns occasionally refuses to be created: every row has a hard limit of 65,535 bytes, and VARCHAR(1000) counts against it even when you store three characters.

ENUM and SET, briefly

ENUM('pending','paid','failed') stores one value from a fixed list as a 1-byte index, which makes it compact and readable at the same time. SET does the same for combinations, storing up to 64 members as a bitmask. Both are convenient and both are painful to change later — adding a value to an ENUM rewrites the column definition, and reordering the list silently reinterprets every existing row. If the list might grow, a lookup table with a foreign key is the safer shape.

What's next

That is the whole first layer: five integer sizes, four decimal types and a family of string types, each one a trade between range, precision and bytes. None of it is hard — it is just the part everyone skips on the way to the interesting stuff.
